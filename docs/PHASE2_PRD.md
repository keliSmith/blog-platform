# 博客内容平台 — Phase 2 新功能产品规格文档（PRD）

> **文档状态**：Draft v1 · **作者**：产品通 · **适用项目**：blog-platform（React 18 + Vite + antd 6 前端 / FastAPI + MySQL 后端）
> **背景**：Phase 1 已交付文章 CRUD、草稿/发布、富文本编辑器（Tiptap + KaTeX）、分类/标签、评论、收藏、点赞、双语言 i18n、暗/亮主题、JWT 鉴权与基础后台。本文档基于代码现状盘点，识别并规格化 Phase 2 应补的"互动 / 运营 / 信任 / 数据"四类缺口。

---

## 1. 问题陈述（Problem Statement）

平台当前已完成"写文章—发文章—看文章"的最小闭环，但缺少支撑**长期留存、可被发现、可运营、可信赖**的能力：

- 作者发布文章后**没有任何反馈通道**（读者评论/点赞/关注无法触达作者），导致创作者缺乏正循环激励。
- 站点**对外不可被搜索引擎与 RSS 订阅发现**（无 OG 标签、无 sitemap、无 RSS），自然流量为 0。
- 后台**无法管理用户、无法配置站点信息**（无用户管理、无站点设置），运营依赖改代码。
- 图片上传后**无法统一管理与复用**（无媒体库），编辑效率低。
- 新用户注册即默认 `email_verified/phone_verified = true`，**验证流程形同虚设**；且**无任何防刷/举报/限流**机制，内容安全处于裸奔状态。
- 数据分析仅停留在"总数"，**无单作者维度、无时间序列**，无法指导运营。

如果不补齐，平台将停留在"能用的 Demo"，难以进入真实运营与增长阶段。

---

## 2. 目标（Goals）

1. **建立创作者正循环**：作者能收到评论/点赞/关注通知，30 天内活跃作者人均收到 ≥ 3 条互动通知。
2. **可被外部发现**：上线 SEO（OG/sitemap/RSS）后 60 天内搜索引擎收录文章 ≥ 80%，RSS 订阅可正常拉取。
3. **运营自助化**：后台支持用户管理（封禁/角色）与站点设置（标题/Logo/SEO），运营不再改代码。
4. **内容资产化**：媒体库支持上传/查询/删除复用，编辑上传图片平均耗时下降 ≥ 50%。
5. **可信赖与安全**：上线防刷（验证码/限流）+ 内容举报，垃圾内容占比 < 1%。
6. **数据可决策**：提供单作者维度 + 趋势视图，运营周报可自动产出。

---

## 3. 非目标（Non-Goals）

1. **不引入第三方评论系统**（如 Disqus）：保持自研、掌控数据。
2. **不做付费/订阅/打赏商业化**：Phase 2 聚焦留存与运营，变现延后。
3. **不重写 Phase 1 编辑器**：仅补充导入/导出与表格增强，不重构核心。
4. **不做多租户/SaaS 化**：本期仍是单一站点，不考虑站点隔离。
5. **不做移动原生 App**：仅保证现有 Web 响应式可用，不做 iOS/Android。
6. **不接入真实短信网关**：SMS 仍走 console 兜底（见 §9），仅补全 UI 流程。

### 4.1 站内通知系统（In-App Notification）— P0

**Why**：当前 `notifications.py` 仅有验证码发送 stub，无任何"用户行为 → 接收者"通知。这是创作者正循环的核心。

**用户故事**
- 作为**作者**，我希望在有人评论我的文章时收到通知，以便及时互动。
- 作为**作者**，我希望在有人点赞/收藏我的文章时收到通知，以便感知价值。
- 作为**读者**，我希望在关注的作者发布新文章时收到通知，以便持续消费。
- 作为**用户**，我希望通知有未读红点、可一键已读/清除，以便不被打扰。

**需求**
- **P0**
  - 新增 `notifications` 表：`id, user_id, type, payload(json), is_read, created_at`。
  - 触发源：评论（含回复）、点赞、收藏、新关注、文章通过审核（若启用审核）。
  - 接口：`GET /api/notifications`（分页 + 未读数）、`POST /api/notifications/read`、系统铃铛组件（Header）+ 未读角标。
  - 仅通知**接收方本人**，评论通知发给文章作者 + 被回复人。
- **P1**
  - 通知聚合（同一文章多条评论合并为"N 条新评论"）。
  - 邮件通知（复用现有 SMTP）作为可选项，频率可配置（即时/每日汇总）。
- **P2**
  - WebSocket 实时推送（替代轮询）；通知偏好设置页。

**验收标准**
- AC1：评论发布后，文章作者登录即见未读红点，点开可见"用户X评论了《标题》"。
- AC2：点赞/收藏/关注均生成对应通知，且不通知触发者本人。
- AC3：标记已读后角标归零；"全部已读"一键生效。
- AC4：通知列表分页正常，无 N+1 查询（后端已用 async SQLAlchemy，注意 lazy 关系）。

### 4.2 搜索引擎优化与可发现性（SEO / OG / Sitemap / RSS）— P0

**Why**：当前 `index.html` 为静态模板，无任何动态 meta；无 sitemap/RSS，外部流量入口为 0。

**用户故事**
- 作为**读者**，我希望把文章分享到社交平台时显示标题/封面/摘要，以便吸引点击。
- 作为**站点运营**，我希望搜索引擎能收录文章、读者能用 RSS 订阅，以便自然增长。

**需求**
- **P0**
  - 详情页动态注入 `<title>`、`description`、`og:title/description/image`、`article:published_time`（前端用 `react-helmet-async`，不引入额外 UI 库）。
  - 后端 `GET /sitemap.xml`：列出已发布文章（含 lastmod）+ 分类页。
  - 后端 `GET /feed/rss.xml`：最新 N 篇已发布文章（RSS 2.0）。
- **P1**
  - 文章结构化数据（JSON-LD `Article` schema）。
  - `robots.txt` 声明 sitemap 位置。
- **P2**
  - 自动提交 sitemap 至 Bing/Google（需 API key，非本期必做）。

**验收标准**
- AC1：分享文章链接到支持 OG 的客户端，抓取到的标题/封面/描述正确。
- AC2：访问 `/sitemap.xml` 返回合法 XML，包含所有 `published` 文章。
- AC3：访问 `/feed/rss.xml` 返回合法 RSS，条目含标题/链接/摘要/发布时间。
- AC4：草稿/已删除文章**不**出现在 sitemap 与 RSS 中（沿用 `_assert_visible` 守卫）。

### 4.3 媒体资源库（Media Library）— P1

**Why**：当前 `upload.py` 仅支持一次性上传（头像/封面/正文内联），无列表/删除/复用，作者反复传同一张图。

**用户故事**
- 作为**作者**，我希望在编辑器里从已有图片库选择图片，以便复用、不重复上传。
- 作为**作者**，我希望能删除/重命名已上传的图片，以便管理我的内容资产。

**需求**
- **P0（最小可用）**
  - 新增 `media_assets` 表：`id, user_id, url, filename, size, width, height, created_at`。
  - 接口：`GET /api/media`（本人分页列表）、`DELETE /api/media/<id>`（仅本人/admin）。
  - 编辑器插入图片时支持"从媒体库选择"与"新上传"两种入口。
- **P1**
  - 非图片文件（PDF 等）上传与托管（需扩展 `upload.py` 校验白名单）。
  - 缩略图/原图分离存储（沿用现有压缩逻辑）。
- **P2**
  - 媒体库管理页（网格视图、批量删除、按大小/时间排序）。

**验收标准**
- AC1：上传过的图片出现在媒体库列表，可再次插入任意文章。
- AC2：删除某图片后，其 URL 在媒体库不可见；已在文章内联引用的图片**不**强制删除（避免文章破图，仅提示）。
- AC3：非本人无法删除他人媒体资源（返回 403）。

### 4.4 后台用户管理与站点设置（Admin Console）— P0

**Why**：当前 `admin.py` 仅有文章/评论管理，无用户管理、无站点配置端点，运营靠改代码。

**用户故事**
- 作为**管理员**，我希望查看/搜索/封禁用户、修改角色，以便处理违规与分配权限。
- 作为**管理员**，我希望配置站点标题、Logo、默认 SEO 描述、社交链接，以便统一品牌。

**需求**
- **P0**
  - 新增 `GET/PUT /api/admin/users`（列表+分页+搜索+封禁/解封+角色变更，限 admin）。
  - 新增 `site_settings` 表（KV 或单行）：`site_title, logo_url, default_description, social_links(json), icp(备案号)`。
  - 接口 `GET/PUT /api/admin/site-settings`；前端 `pages/admin/*` 增加"用户管理""站点设置"两个页签。
- **P1**
  - 用户操作审计日志（封禁/角色变更留痕）。
  - 站点设置影响的 OG 默认值回灌 §4.2。
- **P2**
  - 角色细分（编辑/运营），不止 admin/user 两档。

**验收标准**
- AC1：管理员可列出全部用户，按用户名/邮箱搜索，封禁后该用户登录被拒（401）。
- AC2：修改站点标题后，未设 OG 的文章默认使用新标题。
- AC3：非 admin 调用用户管理接口返回 403。

### 4.5 互动增强：相关文章与社交分享（Engagement）— P1

**Why**：详情页目前只有"目录 + 复制链接"，无相关推荐、无真实分享按钮，读者看完即走。

**用户故事**
- 作为**读者**，我希望在文章底部看到相关文章，以便连续阅读。
- 作为**读者**，我希望一键分享到微信/X/微博，以便传播。

**需求**
- **P0（相关文章）**
  - 后端 `GET /api/articles/<id>/related?limit=5`：基于同分类 + 共享标签 + 标题相似度（简单 Jaccard/余弦）排序。
  - 详情页底部横向卡片列表（复用现有 `ArticleCard` 组件，保证 3 列一致）。
- **P1（社交分享）**
  - 分享面板：复制链接（已有）+ 微信（二维码弹窗）+ X/Twitter + 微博（各用官方 share intent URL）。
  - 分享按钮仅在文章 `published` 态显示。
- **P2**
  - "猜你喜欢"个性化（基于阅读历史），需先有 §4.1+ 埋点。

**验收标准**
- AC1：每篇文章底部至少展示 3 篇相关文章，空结果优雅降级（不展示区块）。
- AC2：点击 X/微博分享跳转对应 share URL 且携带来源链接。
- AC3：相关文章不重复展示当前文章本身。

### 4.6 评论增强（Comments Enhancement）— P1

**Why**：评论已支持嵌套回复与 admin 审核，但作者无通知（见 §4.1）、不能编辑、缺举报。

**用户故事**
- 作为**评论者**，我希望编辑/删除自己的评论，以便修正笔误。
- 作为**读者**，我希望举报违规评论，以便维护社区质量。
- 作为**管理员**，我希望在后台处理被举报评论，以便及时处置。

**需求**
- **P0**
  - 评论 `PUT /api/comments/<id>`（仅本人，限发布后 10 分钟内可编辑）。
  - 评论举报 `POST /api/comments/<id>/report`（reason 枚举），入库 `comment_reports`。
- **P1**
  - 后台举报处理队列（`admin.py` 扩展）：标记处理/删除原评论。
  - 评论触发作者通知（依赖 §4.1）。
- **P2**
  - @提及 与 表情反应。

**验收标准**
- AC1：本人可在时限内编辑评论，超时被拒（403/409）。
- AC2：举报后该评论进入后台待处理列表，处理记录可查。
- AC3：被举报且被管理员删除的评论对普通读者不可见。

### 4.7 信任与安全：防刷与限流（Trust & Safety）— P0

**Why**：当前仅注册验证码有重发限速（`auth.py:53`），评论/文章/点赞无任何防护，且短信验证码为 console 兜底，易被滥用。

**用户故事**
- 作为**运营**，我希望限制单用户单位时间内的发布/评论频率，以便阻止机器人刷屏。
- 作为**管理员**，我希望对高风险操作加验证码，以便降低滥用。

**需求**
- **P0**
  - 全局限流中间件：评论/文章创建/点赞按 `user_id + action` 维度限速（如评论 1 次/5s、文章 5 篇/小时），返回 429 + 友好文案。
  - 公共接口（注册、搜索）按 IP 限速（Redis，已在 Docker Compose 中）。
  - 评论发布接入图形/滑动验证码（推荐前端 `react-turnstile` 或 hCaptcha，不引入重型 UI 库）；密钥走环境变量。
- **P1**
  - 敏感词过滤（评论/文章标题）基础词表 + 命中标记。
  - 风险评分（同 IP 多账号、短时间高频）。
- **P2**
  - 设备指纹；与第三方反垃圾（如 Akismet）对接。

**验收标准**
- AC1：同一用户 5 秒内连续发两条评论，第二条被拒（429）。
- AC2：未通过验证码的评论请求被拒（403）。
- AC3：限流对正常用户无感（阈值经压测确认）。

### 4.8 邮件 / 手机验证全流程（Verification Flow）— P1

**Why**：`email_verified/phone_verified` 字段注册时直接置 True，验证名存实亡。需补全真实流程与 UI。

**用户故事**
- 作为**新用户**，我希望注册后通过邮件/短信验证码完成验证，以便账号更安全、解锁全部功能。
- 作为**用户**，我希望未验证时看到引导，验证后可解除限制。

**需求**
- **P0**
  - 注册时 `email_verified/phone_verified` 默认 **False**；发送验证邮件（复用 SMTP），含失效链接/token。
  - `GET/POST /api/auth/verify-email?token=`、`POST /api/auth/resend-verify`（带限速）。
  - 前端：个人资料页显示验证状态徽标 + 重发按钮 + 未验证引导条。
- **P1**
  - 手机验证流程（UI 与邮件对称；SMS 仍 console 兜底，见 §3 非目标）。
  - 未验证账号限制敏感操作（发公开评论/收藏），并提示去验证。
- **P2**
  - 验证后奖励（如解锁自定义域名/高级编辑器）。

**验收标准**
- AC1：新注册用户两字段为 False，点击邮件链接后变为 True。
- AC2：重发验证邮件受限速保护，不会无限刷。
- AC3：未验证用户在受限操作时收到明确引导，而非静默失败。

### 4.9 作者维度分析（Author Analytics）— P2

**Why**：`statistics.py` 仅有全站 hot/总数，admin dashboard 也只见汇总。作者看不到自己文章表现。

**用户故事**
- 作为**作者**，我希望看到我每篇文章的阅读/点赞/收藏趋势，以便优化内容。
- 作为**运营**，我希望看全站趋势图，以便做周报。

**需求**
- **P0（作者视图）**
  - `GET /api/analytics/author/me`：本人文章聚合（ views/likes/favorites 时间序列，按日/周）。
  - 个人中心新增"数据"页签（折线图，复用 antd 组件即可，不引图表库除非必要）。
- **P1（运营视图）**
  - 全站趋势 + Top 文章/作者排行，回灌 admin dashboard。
  - 阅读来源/设备分布（需补充埋点，见 §4.7 风险）。
- **P2**
  - 实验/AB 框架；导出 CSV。

**验收标准**
- AC1：作者可见自己近 30 天阅读趋势折线，数据与文章详情页 `ArticleView` 计数一致。
- AC2：仅本人/管理员可见对应数据，跨用户访问返回 403。

## 5. 优先级与分期（Prioritization & Phasing）

按"用户价值 × 工程可行性 × 风险缓解"粗排（RICE 简化版）：

| 功能域 | 等级 | 建议分期 | 关键依赖 |
|---|---|---|---|
| 4.1 站内通知 | P0 | Phase 2a | 无 |
| 4.2 SEO/RSS/Sitemap | P0 | Phase 2a | 无 |
| 4.4 后台用户管理+站点设置 | P0 | Phase 2a | 无 |
| 4.7 防刷与限流 | P0 | Phase 2a | Redis（已就绪） |
| 4.3 媒体库 | P1 | Phase 2b | 无 |
| 4.5 相关文章+分享 | P1 | Phase 2b | 4.1（分享埋点） |
| 4.6 评论增强 | P1 | Phase 2b | 4.1（通知）、4.7（举报限速） |
| 4.8 验证全流程 | P1 | Phase 2b | 无 |
| 4.9 作者分析 | P2 | Phase 2c | 4.7 埋点 |

**建议节奏**：2a 先把"可信 + 可见 + 可达"打底（通知/SEO/后台/防刷），2b 做"互动与运营效率"，2c 做"数据驱动"。每期控制在 2–3 周可交付。

## 7. 开放问题（Open Questions）

- **Q1（工程）**：通知实时性——Phase 2a 先用轮询还是直接上 WebSocket？轮询成本低、先上线，WebSocket 放 P2，是否同意？

## 8. 风险与依赖（Risks & Dependencies）

- **Redis 依赖**：§4.7 限流与 §4.1 实时推送依赖 Redis；Docker Compose 已含 Redis 7，自建/SQLite 测试环境需 mock 或跳过（测试用内存限速器）。
- **第三方验证码**：§4.7 需要 Turnstile/hCaptcha 站点密钥，上线前需申请；测试环境可开关。
- **隐私合规**：§4.9 埋点与 §4.8 验证邮件触发需遵循个人信息保护法，默认收敛采集。
- **SMS 网关**：§4.8 手机验证本期仍 console 兜底，不阻断流程，但生产环境验证短信实际不发送——需在发布说明中标注此限制。
- **范围控制**：严格按 Non-Goals 拒绝变现/多租户/App，避免 2a 膨胀。
